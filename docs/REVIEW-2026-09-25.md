# THE TEN SUGGESTIONS

## 1. Make the bridge fail closed — right now any host on the LAN can read `~/.hermes` and run shell commands

**(1) What to change.** Refuse to start without `BRIDGE_TOKEN`; move `/html/` behind a signed,
expiring link and restrict it to a previews directory; check the token before `websocket.accept()`;
stop advertising `Access-Control-Allow-Origin: *`; bind to loopback/Tailscale instead of `0.0.0.0`.

**(2) Evidence.** `BRIDGE_TOKEN` is optional (`server/bridge.py:50`) and the auth middleware only
guards `/api/v1` (`server/bridge.py:98-104`). I proved the hole with the bridge running as-is:

```
/html/home/hermes/.hermes/config.yaml -> HTTP 200, 6595 bytes
/html/home/hermes/.hermes/.env        -> HTTP 200, 25177 bytes
/html/home/hermes/.hermes/state.db    -> HTTP 200, 143994880 bytes
/api/v1/status                        -> HTTP 401          (control: auth works on /api/v1)
ss -ltnp | grep 9130  ->  LISTEN 0.0.0.0:9130
```

Those requests carried **no `Authorization` header at all**. Mechanism:
`server/bridge.py:743-759` — "Deliberately OUTSIDE `/api/v1` so it needs no auth header", and
`_file_roots()` (`server/bridge.py:710-724`) always includes the whole `~/.hermes` home; unknown
suffixes are still served as `application/octet-stream` (`server/bridge.py:758`). `0.0.0.0` binding
is `server/bridge.py:2256`; CORS `*` is `server/bridge.py:93-95`. The WebSockets
(`server/bridge.py:835`, `:876`) never authenticate because `@app.middleware("http")` does not run
for the WebSocket scope. `/api/v1/terminal/run` executes with `shell=True`
(`server/bridge.py:1504-1530`) — its input validation is real but cosmetic (length ≤ 8000 at
`:1512`), because the whole endpoint is unauthenticated whenever the token is unset.

**(3) Implementation.** Fail-closed startup:
`if not BRIDGE_TOKEN: raise SystemExit("BRIDGE_TOKEN required")`. For `/html/`, serve only
`HERMES/previews` and `MER_FILES_ROOTS`, return 404 for anything not in `_PREVIEW_TYPES`, and issue
`?sig=HMAC(BRIDGE_TOKEN, path|exp)&exp=` links the app requests from a logged-in endpoint. Add a
token check in both `ws_*` handlers before `accept()`. Set `allow_origins` explicitly. Default bind
`127.0.0.1`, with `BRIDGE_HOST` for the Tailscale address.

**(4) Effort:** M

**(5) If it stays:** anyone on the LAN — or the Tailscale tailnet, or anything that sees the mDNS
advert that `server/announce_bridge.py` broadcasts — can download the full chat history
(144 MB `state.db`, including every conversation in which a secret was echoed), `.env`, `auth.json`,
and the Firebase service-account key, and can run arbitrary shell commands as the `hermes` user,
which owns the gateway, every bot token and this box's sudo access.

## 2. Rotate the bridge token and stop the plaintext copies — the live token is both world-readable and inside the chat store

**(1) What to change.** Rotate `BRIDGE_TOKEN` (and the SparkyFitness token); delete the world-readable
unit backup; `chmod 700 ~/.hermes/secrets/`; move unit secrets into an `EnvironmentFile` with 0600;
scrub the token from `state.db`; add a scan that can fail.

**(2) Evidence.** I grepped for the live 48-character token from the deployed unit and found it in
the Hermes chat store — by row, not by eyeball:

```
state.db messages rows containing the live BRIDGE_TOKEN: 2
  id=2935 session=20260830_152531_a95d40 role=user content_len=6441
  id=3452 session=20260831_052208_cc4dea role=tool content_len=1237
```

and in a **world-readable** unit backup:

```
-rw------- (0600)  hermes-bridge.service                     <- live unit
-rw-rw-r-- (0664)  hermes-bridge.service.bak-1789206915      <- IDENTICAL live token
```

Also verified: `~/.hermes/secrets/` is `0775` and `mercury-fcm-service-account.json` is `0664`;
`config.yaml:189` and `config.yaml:193` hold live MCP bearer tokens in plaintext, and
`config.yaml:85` holds the dashboard session secret in plaintext. Combined with finding 1, that
token is retrievable by any LAN host from `/html/home/hermes/.hermes/state.db`. The Opus pass
independently reached the same `.bak`/`secrets/` conclusion.

**(3) Implementation.** Rotate both tokens. `rm` the `.bak`. `chmod 700 ~/.hermes/secrets` and
`chmod 600` every file in it. Replace the unit's inline `Environment=...TOKEN=...` lines with
`EnvironmentFile=%h/.hermes/secrets/bridge.env` — the pattern `claude-web.service` already uses with
`~/.hermes/secrets/claude-web.env` (0600, verified). Delete the two `state.db` rows (or run the
compaction path) and add a `gitleaks detect` step plus a pre-commit hook — that is the check that
can fail.

**(4) Effort:** M

**(5) If it stays:** the token that guards the bridge is readable by any local user and sits in a
file that `hermes`'s own MCP/lint tooling copies around; every future unit edit writes another
`.bak`. Any process that reads `state.db` — including every session, every bot and the whole
`/api/v1` surface — gets the credential.

## 3. Sign the release APK with a real key — it is currently signed with the public Android debug key

**(1) What to change.** Create a release keystore, wire it through `key.properties`, replace the
debug signing config, and add a CI gate that verifies the signing certificate and fails on a
mismatch.

**(2) Evidence.** I ran `apksigner` against the real artifacts:

```
build/app/outputs/flutter-apk/app-release.apk
  Signer #1 certificate DN: CN=Android Debug, O=Android, C=US
  Verified using v1 scheme: false
  Verified using v2 scheme: true
  Verified using v3 scheme: false
~/.hermes/deliveries/Mercury-v2.0.5.apk -> CN=Android Debug, O=Android, C=US
~/Mercury-v2.0.3.apk                    -> C=US, O=Android, CN=Android Debug
```

The certificate SHA-256 matches `~/.android/debug.keystore` (alias `androiddebugkey`, well-known
store/key password `android`). So every published Mercury APK is signed with a key whose private
half is public, and the same key is the default on every Android dev machine. Mechanism: the
Flutter template TODO is still in place —

```kotlin
// android/app/build.gradle.kts
release {
    // TODO: Add your own signing config for the release build.
    // Signing with the debug keys for now, so `flutter run --release` works.
    signingConfig = signingConfigs.getByName("debug")
}
```

— and the release job builds and publishes with no keystore and no verification
(`.github/workflows/ci.yml:74-79`). `grep -rn keystore android/` returns nothing: no keystore
config exists anywhere in the repo.

**(3) Implementation.** `keytool -genkeypair` into `~/.hermes/secrets/mercury-release.jks`, add
`android/key.properties` (gitignored) read by `build.gradle.kts`, set
`signingConfig = signingConfigs.getByName("release")`, and add a CI step:
`apksigner verify --print-certs build/.../app-release.apk | grep -q "CN=…"` — asserting the release
DN **and** v1+v2+v3 schemes present. Keep one keystore per app, as the delivery convention requires,
so in-place updates work.

**(4) Effort:** S/M

**(5) If it stays:** anyone can build a trojaned Mercury Messenger that Android will install as an
in-place update over the real one, inheriting its secure-storage vault and its bridge token
(`lib/core/security/vault.dart`). Android also refuses in-place updates signed by a different key —
which is exactly why the debug key was chosen — so rotating later means every user reinstalls by
hand. This is the "APK published with broken signing" incident, still live.

## 4. Make generated artifacts conform to a recorded real schema — 7 client calls hit endpoints the bridge does not implement, and the guessed-endpoint pattern is what caused the 401s and the Tasker import failure

**(1) What to change.** Add recorded-schema contract tests in both directions (client↔bridge, and
bridge↔external APIs), and validate generated files against a captured golden sample instead of a
hand-written spec. Then implement or delete the phantom calls.

**(2) Evidence.** I diffed the client's calls against the bridge's routes programmatically
(`_get/_post/_patch/_delete` and `Uri.parse` in `lib/data/hermes_repository.dart` vs every
`@app.<verb>` in `server/bridge.py`):

```
CLIENT PATHS WITH NO MATCHING SERVER ROUTE
  /api/v1/cron/{id}            /api/v1/memory/{id}
  /api/v1/servers/{id}         /api/v1/skills/{id}/toggle

METHOD MISMATCH
  POST /api/v1/servers   server_has=GET      (bridge.py:1230)
  POST /api/v1/cron      server_has=GET      (bridge.py:928)
  POST /api/v1/memory    server_has=GET      (bridge.py:992)
```

Client side: `hermes_repository.dart:84,87` (update/remove server), `:78` (add server), `:557,563,566`
(create/edit/delete cron job), `:589` (toggle skill), `:601,607` (add/delete memory). Every one of
those is a 405 or 404, thrown as a bare `Exception`, and swallowed by the UI (finding 5). The app's
"add server", "add memory", "create cron job" and "toggle skill" flows are dead code.

The same class produced two named incidents. `server/bridge.py:1648-1657` guesses SparkyFitness
endpoints — it tries `/api/goals/for-date?date=…`, then falls back to `/api/goals/by-date/{date}`,
and maps 401/403 to "sparky unreachable" — i.e. an invented path is indistinguishable from a bad
credential, which is how a guessed `/api/v1` 401s. And Jokarz-Timeclock's Tasker export was
hand-written XML that Tasker rejected; `docs/TASKER-FORMAT.md` records the exact error ("Import
failed… Error details: Missing event type") and lists the four real captures it was rebuilt from.
The fix that worked there is the pattern to generalise: a captured artefact in the repo
(`app/src/test/resources/tasker/Jokarz_Timeclock.prf.xml`) plus a test that pins the contract
(`TaskerContractTest.kt`).

**(3) Implementation.** A `tools/contract_check.py` in the bridge repo that re-derives both route
sets (as the throwaway script I wrote does) and exits non-zero on drift, wired into
`.github/workflows/ci.yml`. For external APIs, record one real response per endpoint into
`server/tests/fixtures/` and assert the parser against it; delete the guessed fallback list and fail
loudly, distinguishing 401 (credential) from 404 (path). Then either implement the 7 routes or
remove the client methods.

**(4) Effort:** S/M

**(5) If it stays:** the app quietly ships management screens that cannot work, and the next
integration is again written against an assumed schema — the failure mode that has already cost a
plant-format rewrite (Tasker) and a debugging cycle on a 401 that was really a wrong URL.

## 5. Surface failures — today the app swallows them and the delivery path drops payloads with only a log line

**(1) What to change.** One error type that carries the server's own message, rendered in the UI; and
one preflight size check that names the effective cap before an upload starts.

**(2) Evidence.** `lib/state/app_state.dart` swallows errors in eight places —
`:137, :220, :301, :318, :371, :388, :395, :491` are all literally `catch (_) {}`. So a 405 from
finding 4, a 401, or a dead socket produce no user-visible signal at all. Where errors *are*
rethrown, the server's explanation is discarded:
`lib/data/hermes_repository.dart:40` — `throw Exception('GET $path → ${res.statusCode}')` — drops the
`detail` the bridge carefully provides (`{"detail": "path outside allowed roots"}` at
`server/bridge.py:734`, `{"detail": "unauthorized"}` at `:103`). On the delivery side, oversize
artifacts are dropped with a warning only (`gateway/relay/media.py:185-186`), and the caps contradict
each other across paths: **1 MB** webhook bodies (`gateway/platforms/bluebubbles.py:94`,
`gateway/platforms/msgraph_webhook.py:43`), **25 MB** relay media (`gateway/relay/media.py:50`),
**25 MB** kanban attachments (`hermes_cli/kanban_db.py:162`), **32 MB** Discord
(`hermes_cli/config_defaults.py:2434`), **128 MB** inbound (`gateway/platforms/base.py:800`). That
inconsistency is the mechanism behind "large chat attachments silently truncating (22 MB → 1 MB)":
whether a file is delivered, shrunken, or disappears depends on which path it takes, and nothing
tells the user which cap applied.

**(3) Implementation.** Replace `_get/_post/...` throws with `ApiFailure(status, path, detail)` parsed
from the JSON body, and replace each `catch (_) {}` with a `setError(...)` that drives a persistent
error banner plus an in-app Logs view over a bounded ring buffer. Add a single
`effective_attachment_limit(transport)` helper in Hermes, call it in the upload preflight, and return
the cap and the transport name in the failure message ("Mercury: 25 MB limit on relay media; file is
22 MB — use the release download or the LAN URL").

**(4) Effort:** M

**(5) If it stays:** every real failure looks like "nothing happened". The owner cannot distinguish
"the bridge is down" from "the endpoint does not exist" from "the file was too big", which is the
single biggest time cost in debugging this stack.

## 6. Give the gate teeth — the whole test suite is one test that cannot fail, and the delegation runner has no test-count baseline

**(1) What to change.** Make the delegation runner compare test counts and test names before and
after a run, and make the repo's CI assert a minimum test count. Treat an unchanged count as a
failed pass.

**(2) Evidence.** `test/widget_test.dart:6-11` is the **only** test file in the repo:

```dart
testWidgets('StatusMessage renders its title', (tester) async {
  await tester.pumpWidget(const MaterialApp(
    home: Scaffold(body: StatusMessage(title: 'Hello', icon: Icons.check)),
  ));
  expect(find.text('Hello'), findsOneWidget);
});
```

`flutter test` → `+1: All tests passed!`; `flutter analyze` → `No issues found!`. That test asserts a
widget renders the string it was handed — it can only fail if the widget stops rendering text
altogether. It cannot fail for any logic change in the bridge, the chat streaming, the vault, the
group fan-out, or the coach maths. `.github/workflows/ci.yml:28-29` makes that the gate for the whole
product. And `~/.hermes/scripts/code_task.py` runs `--verify`, prints the last 15 lines and the exit
code (`code_task.py:~200-215`), with **no before/after test count and no diffstat** — so "gate went
green, nothing was built" is not detectable from its output, which is exactly the reported incident.

Independent confirmation that agent reports cannot be the evidence: the Opus pass for this review
reported as a critical finding that "`server/hermes-bridge.service` is tracked in git and contains an
18-character **real** (not placeholder) `BRIDGE_TOKEN` … the repo is **PUBLIC**". I checked:
`git log -p --all -- server/hermes-bridge.service | grep BRIDGE_TOKEN` returns exactly one value,
`REPLACE_WITH_TOKEN`, in every revision, and `grep -n BRIDGE_TOKEN` on HEAD confirms it. The repo is
public; the token is a placeholder. The claim was false, and it came from a careful Opus reviewer with
a brief telling it to cite evidence.

**(3) Implementation.** In `code_task.py`, before the run capture
`(test_count, [test names], git rev-parse HEAD, git diff --stat)` by executing the project's own test
command in a count-only mode, capture the same after, print both, and return non-zero if the count
did not increase for a task that claims new tests or if no source file changed. Add an
`assert_test_floor` step to `house-gate.sh` (finding 10) so CI fails when the count drops. Require
every behavioural change to add at least one test that fails without it — the house rule in
`~/.claude/CLAUDE.md` ("A passing suite is not proof your change works") is right but unenforced.

**(4) Effort:** M

**(5) If it stays:** the machine keeps producing green passes that built nothing, and every delegated
report — including confidently wrong ones — has to be re-derived by hand. That is the failure that
cost a whole pass's context.

## 7. Checkpoint the tree automatically around delegated runs — the house rule tells agents *not* to commit

**(1) What to change.** Have the delegation wrapper take a checkpoint before and after every run
(commit or stash-bundle), print the dirty-file count and diffstat, and refuse to declare success on a
dirty tree unless explicitly allowed.

**(2) Evidence.** `~/.claude/CLAUDE.md` is read by every delegated agent
(`code_task.py` passes `~/.claude` via `SHARED_READ_DIRS`, `code_task.py:38-39`) and it says:
"Never `git push --force`, never rewrite published history, **and never commit or push unless the
task explicitly asks for it**." Meanwhile `code_task.py` never commits, never runs `git status`
before or after, and never preserves a patch; it runs the agent with
`--dangerously-skip-permissions` (`code_task.py:~86`). So a delegated pass that modifies a tree and
then dies leaves exactly the residue described — and I ran into it on this very job: the repo I was
sent to update had a modified `android/gradle.properties` sitting uncommitted (`git status -sb` →
` M android/gradle.properties`), which I committed as `efb6e19`. `config.yaml:31-32` has
`checkpoints.enabled: true` as the only net, and the incident report says work had to be recovered by
hand twice.

**(3) Implementation.** In `code_task.py`: `git -C repo status --porcelain` before and after; if
dirty after, write a bundle (`git bundle create /tmp/run-<ts>.bundle HEAD` plus
`git stash create`) and print the diffstat; add a `--checkpoint` default that commits the agent's work
as `wip(delegate): <task>` with the agent/session id in the body; and keep the no-push rule (never
push). Relax the `~/.claude` line to "do not commit *unless this wrapper is driving you*, in which
case the wrapper commits for you".

**(4) Effort:** S

**(5) If it stays:** every crash repeats the two hand recoveries, and a large uncommitted tree can be
destroyed by the next `git checkout` — which is what happened.

## 8. Persist every delegated pass as a file — findings that only exist in stdout are findings that get lost

**(1) What to change.** Always write a run artifact (report + verify output + diffstat + git state +
test counts) into the repo, and have the review/roadmap flow consume those artifacts.

**(2) Evidence.** `code_task.py` has no output flag: its only file I/O is *reading* `--prompt-file`
(`code_task.py:138`), and the agent's report is `print(...)`-ed to stdout. I had to hand-write the
brief for this very pass to `~/.hermes/cache/mercury-review-brief.md`. The working record shows the
consequence: of the 31 jobs in `~/.hermes/cron/jobs.json`, **30 are `DISABLED` one-shots** still
carrying their full original prompts (Health OS, Timeclock, TwoRooms, garmin-liftosaur, …) — the
history of what was attempted lives as dead cron rows, not as reports, and "a pass whose findings were
lost because the write-up came last" has no counterpart file to recover from.

**(3) Implementation.** `code_task.py` writes `<repo>/.hermes-runs/<UTC-stamp>-<session_id>.json`
containing: task, agent+model, exit code, interrupted flag, the report text, the `--verify` output
and exit code, `git diff --stat`, `git status --porcelain`, and the before/after test counts; then
prints the path. A small `review_from_runs.py` folds the newest artefacts into the living roadmap.
Add `.hermes-runs/` to the ignore list in every repo.

**(4) Effort:** S

**(5) If it stays:** each pass's reasoning is unrecoverable once the session is compacted or lost, the
roadmap has to be rebuilt from memory, and the 30 dead cron jobs keep growing because there is
nowhere else to put what happened.

## 9. Give the long-running surfaces a unit that is actually enabled, and respect the memory ceiling

**(1) What to change.** Enable the dashboard unit (or bind it to loopback), and put memory limits on
the heavy units so a build cannot take the box down again.

**(2) Evidence.** `config.yaml:80-88` publishes the dashboard on `host: 0.0.0.0`, port 9119, with an
scrypt `password_hash` and a plaintext `secret`. `~/.config/systemd/user/hermes-dashboard.service`
exists — but:

```
systemctl --user is-enabled hermes-dashboard.service  -> disabled
systemctl --user is-active  hermes-dashboard.service  -> inactive
ls ~/.config/systemd/user/default.target.wants/       -> 21 units, dashboard is NOT among them
```

So the unit was written and never enabled; the dashboard still dies with the session. Separately, the
OOM incident is confirmed on this box and still imminent:

```
journalctl --user: "antigravity-cli-daemon.service: Failed with result 'oom-kill'."  (Sep 24 06:52:08)
free -h:  Mem 14Gi total, 735Mi free;  Swap 4.0Gi total, 4.0Gi used, 5.6Mi free
```

The build-killing mechanism was the Gradle daemon allowance (8 G heap + 4 G metaspace + 512 m code
cache ≈ 12 GB for the daemon alone, on a 16 GB box with a full 4 GB swap) — the setting I right-sized
and committed in `efb6e19`.

**(3) Implementation.** `systemctl --user enable --now hermes-dashboard.service`, or change
`config.yaml:86` to `host: 127.0.0.1` and reach it over Tailscale. Add `MemoryMax=` (e.g. 2G) and
`MemoryHigh=` to the delegation-heavy units and `antigravity-cli-daemon.service`, and copy the
`android/gradle.properties` caps into every Gradle repo that builds on this machine.

**(4) Effort:** S

**(5) If it stays:** the monitoring surface is unreachable exactly when it is needed (mid-session),
and the next concurrent build plus a gateway will hit the same swap wall with zero build output —
the OOM kill that already cost one pass.

## 10. Stop hand-rolling per-repo CI — one shared house gate, and commit the Gradle wrapper everywhere

**(1) What to change.** Commit the Gradle wrapper in every Gradle repo, and add a single
`house-gate.sh` that every repo's CI and every delegated run calls.

**(2) Evidence.** My scan of every repo's workflows for `./gradlew` usage vs tracked wrapper files:

```
SparkyFitness-Liftosaur   ci=android.yml   gradlew_tracked=False jar_tracked=False  <== CI CALLS ./gradlew BUT WRAPPER NOT COMMITTED
Jokarz-Timeclock          ci=build-apk.yml gradlew_tracked=True  jar_tracked=True
Simplefin_Android_Finances ci=build.yml,ci.yml ... True/True
lumen                     ci=release.yml    True/True
```

`SparkyFitness-Liftosaur/.github/workflows/android.yml` cannot build: it invokes `./gradlew` and
`git ls-files` tracks neither `gradlew` nor `gradle-wrapper.jar` — the exact reported incident.
`HabitCraftBridge` has `build.gradle.kts` + `settings.gradle.kts`, no wrapper and no `.github/` at
all. `hermes-mobile/android/.gitignore:1` and `:4` deliberately ignore the wrapper (fine for Flutter,
fatal the moment CI calls `./gradlew`). And **no** workflow contains a secret or credential scan,
which is why the token-in-a-`.bak` class (finding 2) and the debug-key signing (finding 3) have no
gate.

**(3) Implementation.** For each Gradle repo: `gradle wrapper --gradle-version <pinned>` and commit
